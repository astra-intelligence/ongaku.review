# PRの作成

このリポジトリの差分からPR本文と設定を準備し、GitHub CLIでDraft PRを作成する。本文の構成は[PRテンプレート](../../../.github/PULL_REQUEST_TEMPLATE.md)を使う。

## 適用範囲

- ユーザーの明示指定を優先する。新規PRの既定はDraftとし、作成後の通常PRへの切り替えは別の依頼で行う。
- プレビューや提案だけの依頼では、本文と設定案を提示する。コミット・push・GitHubへの書き込みは行わない。
- PR作成の依頼では、必要な対象変更のコミットと通常pushまで進める。依頼と関係のない作業は含めない。
- ラベルの新設、force push、マージは既定動作に含めない。

## 作成前の確認

1. リポジトリ内の適用される指示、PRテンプレート、既存のPR運用を確認する。
2. Gitリポジトリ、`gh`、認証、remote、現在のブランチ、作業ツリーを確認し、PRの対象リポジトリとpush先を確定する。Git情報がない場合や対象が曖昧な場合は、不足情報を示して確認する。ディレクトリ名やコミットのメールアドレスからGitHubの所有者・担当者を推測しない。
3. headのブランチとリポジトリが一致する既存のopen PRを確認する。baseは「ユーザーの明示指定 → 既存PR → ブランチの `gh-merge-base` 設定 → GitHubのデフォルトブランチ」の順で決める。複数の候補を絞れなければ確認する。
4. baseとheadのコミット、差分全体、未コミットの対象変更を確認する。本文の根拠にはbaseとのmerge-baseからheadまでの差分を使う。作成時に未コミットの対象変更がある場合は、コミット後の差分を改めて確認する。差分がない場合はPRを作成しない。
5. 同じheadリポジトリ・headブランチ・baseのopen PRがあれば再利用する。既存の通常PRを、このskillの既定値だけを理由にDraftへ戻さない。

## 本文とメタデータの準備

### 本文

- テンプレートの6見出しと順番を維持し、差分に基づいて日本語で記載する。ユーザーが別の言語を指定した場合は、その指定を優先する。
- 概要には解決する問題と変更後の振る舞いを書き、変更内容には主な変更点を書く。ファイル一覧や作業履歴の羅列は避ける。
- 影響範囲には互換性、移行・設定変更、レビューの注目点を必要に応じて記載する。影響や関連Issueがなければ「なし」と書く。未確認の情報は「未確認」と書く。
- 必要な検証を実施し、確認方法と実際の結果を書く。未実施・失敗した検証は理由や結果を記載する。画面変更の画像・動画があれば、確認方法・結果に追加する。用意できない場合は確認すべき画面や操作を説明する。
- チェックリストは実際に確認した項目だけをチェックする。未確認は未チェック、対象外は未チェックのまま理由を添える。人が確認したことを代わりに宣言しない。
- 関連Issueはユーザー指定、作業の文脈、ブランチやコミットから候補を得て、GitHub上の内容を確認する。完全に解決し、baseがデフォルトブランチの場合に `Closes #番号` を使う。部分対応や別のbaseでは `Refs #番号` などの通常参照にする。他リポジトリは所有者・リポジトリも明記する。
- テンプレートの記入案内コメントや例の番号は完成した本文から取り除く。既存PRを更新する場合は、手書きの説明やリンクを保持して、今回の差分に必要な部分だけを更新する。

### メタデータ

| 項目 | 判断基準 |
| --- | --- |
| タイトル | [コミットメッセージの規約](../writing-commit-messages/SKILL.md)のtypeを使い、PR全体の主目的を `<type>: <summary>` で表す。summaryは日本語を既定とし、明示指定を優先する |
| ラベル | 対象リポジトリの既存ラベルと説明を全件取得し、実際の差分の目的・影響と合うものを選ぶ。ラベル名を固定しない。`fix` だから必ず `bug` とするような機械的な対応付けはしない |
| アサイニー | 明示指定、明文化されたリポジトリ規約、それ以外は認証中の自分を `@me` で設定する。既存PRの担当者は保持し、空の場合に既定値を補う |
| レビュアー | 明示指定時に設定する。CODEOWNERSの自動レビュー依頼はGitHubに任せる。Draftでは自動依頼されず、通常PRへの切り替え時に通知される |
| Project・Milestone | 明示指定または明文化された運用がある場合に、実在する対象を確認して設定する |

ラベルに適切な候補がなければ未設定とし、その理由を報告する。優先度、破壊的変更、リリース・backportに関するラベルは、それぞれの意味に合う根拠がある場合だけ選ぶ。指定された名前が存在しない場合や取得に失敗した場合は、その状態を報告し、似た名前への置き換えや新設は行わない。

既存PRのラベル・担当者・レビュアー・Project・Milestoneは、変更や削除の指定がなければ保持する。必要な追加だけを行い、既存の値やGitHubの自動設定を消さない。

## 作成と反映確認

1. プレビューの場合はここで本文、対象のbase・head、Draft、ラベル・担当者などの設定案を提示して終える。`gh pr create --dry-run` はpushを伴う可能性があるため使わない。
2. 必要なコミットは[コミットメッセージの規約](../writing-commit-messages/SKILL.md)に従って作成する。baseブランチ上で作業している場合は作業用ブランチを作ってheadを更新し、対象の変更だけをコミットする。確定したremote・headへ通常pushし、失敗した場合はPR作成へ進まない。
3. 完成した本文をUTF-8の一時ファイルに保存する。`--body-file` を使い、シェルの文字列展開で本文を組み立てない。
4. 作成直前にも既存PRを確認する。新規作成では `--repo`、`--base`、`--head`、`--title`、`--body-file`、`--draft` と、確認済みのメタデータを明示する。既存PRならその番号を指定して必要な部分だけを更新する。
5. 書き込み後は同じPRを再取得し、URL、base・headとheadリポジトリ、タイトル・本文、Draft状態、ラベル、アサイニー、指定したレビュアー・Project・Milestoneが反映されているか確認する。既存値や自動付与の値が増えていても、今回指定した値が反映されていれば保持する。
6. PRのURLと反映済みの設定を報告する。設定不要・候補なしで省略した項目と、失敗・未確認の項目は区別する。CIの実行結果を確認していなければ、成功とは報告しない。

## 途中で失敗した場合

- 作成コマンドが失敗しても、PR自体が作成済みの場合がある。返されたURL・番号、または同じheadリポジトリ・headブランチ・baseを検索して存在を確認する。通信失敗などで存在を判断できない間は作成を繰り返さない。
- PRが存在する場合は、新規作成せず未反映の項目だけを更新する。PRが存在しないことを確認できた場合に、失敗原因を解消してから作成を再試行する。
- 権限不足や無効な設定で同じ操作を繰り返さない。作成済みのPRは保持し、そのURL、反映済みの項目、未反映の項目と理由を報告する。未作成なら、その状態と準備済みの本文を伝える。
